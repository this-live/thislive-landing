Security starts before the demo

April 13, 2026

This week I shipped Agent Fabric, my orchestration layer, and the rollout handed me a lesson about permission boundaries I should have learned earlier.

Why I built it

The reason I built this was practical, not ambitious. My agents run across my machines and can act on files while I am away, so a single sloppy command can touch far more than I meant to change. I care about where an agent is allowed to write as much as what it is allowed to do.

The tools

Agent Fabric is what installs and runs my agents across my machines. It carried a memory bridge, called supermemory, to Claude Desktop and Codex, my two coding agents, so they could finally read my notes. It also started syncing my code to my file server and reporting what it touched, so I could see what the agents were actually doing.

What I learned

I was wrong about one command. It was labeled read-only, and I assumed the label meant it was safe. It was actually editing tracked documents on my machines. I only caught it because I happened to review what it was changing that day, and nothing failed or warned me. The honest version is that a person was the guardrail, not the software. I removed the line that let it write in a single edit. Since then, whenever the rollout meets a task it cannot safely complete, it stops and drops the blocker into a queue for me to deal with, instead of quietly working around it.

What I have not solved

Here is what I have not solved. Nothing stops me from writing another command I call read-only that actually writes. There is no automated test that inspects a command and confirms it changes no files. Until there is, the only thing keeping my tools in their lane is me checking each change by hand, and I am the weakest link in that chain.
